# 0. Что такое SERAPHIM

SERAPHIM — локально управляемая, модульная AI-среда, объединяющая модели, инструменты, приложения, память, навыки, автоматизацию и визуальный интерфейс. Это не просто чат с инструментами и не один конкретный LLM. Модель — заменяемый интеллектуальный компонент; SERAPHIM отвечает за надёжный жизненный цикл задач, права, состояние, память, планирование, проверку результата, остановку циклов, восстановление, интеграции и UI.

В целевом состоянии пользователь сможет:

- работать с облачными, локальными и собственными моделями через единый интерфейс;
- задавать цели и поручать многошаговые задачи с проверяемым результатом;
- подключать программы, даже если готового MCP нет;
- создавать адаптеры, MCP-инструменты и Skills, просматривать и менять их код;
- управлять проектами, файлами, памятью, моделями, MCP, разрешениями и внешним видом из GUI или CLI;
- прерывать задачу, продолжать позже и видеть, что сделано и на чём основан результат;
- хранить конфигурацию, идентичность и пользовательские компоненты в едином корне;
- расширять систему без переписывания ядра.

Название и эстетика отсылают к линии **The Last Seraph → SERAPHIM → APOCRYPHA**. Это художественная мифология продукта, а не утверждение о сознании, сверхъестественных возможностях или безошибочности ИИ.

## 0.1. Архитектурная формула

```text
SERAPHIM = Runtime + Models + Tools + Memory + Skills + Interfaces + Safety + Verification
```

Модель предлагает решения. Runtime управляет выполнением. Инструменты воздействуют на внешний мир. MEMORY сохраняет контекст. Skills задают воспроизводимые процедуры. AEGIS ограничивает действия. Verification проверяет достижение цели. UI делает происходящее наблюдаемым.

## 0.2. Инварианты

1. Модель не является источником истины о состоянии задачи: состояние хранится в runtime/БД.
2. Модель не выдаёт себе разрешения: доступ независимо проверяет AEGIS.
3. Вызов инструмента не равен успешному результату: значимые действия требуют проверки постусловия.
4. Память не равна истине: у записей должны быть источник, дата, scope и при необходимости уверенность.
5. Skill — видимый, версионируемый и отключаемый артефакт, а не скрытая часть system prompt.
6. MCP — один из интерфейсов интеграции, не вся архитектура.
7. Конфигурация пользователя хранится внутри корня SERAPHIM, если пользователь не выбрал другое место.
8. GUI и CLI управляют одним состоянием и проходят одну валидацию.
9. Внешние компоненты недоверенны по умолчанию.
10. Длительная задача объяснима через события, действия и доказательства; скрытое рассуждение модели не выдаётся за гарантированно достоверный отчёт.
11. Возможность отделена от гарантии: обнаруженный интерфейс приложения ещё не означает полную совместимость.
12. Разработка ведётся вертикальными сценариями: сначала рабочее ядро, затем сложная автономность.

# 1. Продуктовые принципы

## 1.1. Открытость

Пользователь может читать, редактировать, экспортировать и проверять system prompt, личность, Skills, настройки провайдеров, MCP, политики, темы, локализации и manifests интеграций. Скрытая магия не является условием работы системы. Секреты при этом не обязаны храниться открытым текстом: они могут быть в защищённом хранилище или зашифрованном файле внутри корня, но расположение и способ управления должны быть видны пользователю.

## 1.2. Заменяемость

Замена Qwen на облачную модель, Strata на другой сервер, одного MCP на другой или тёмной темы на светлую не должна ломать task engine, память и права доступа.

## 1.3. Видимость

SERAPHIM показывает выбранную модель, активный план и шаг, вызванные инструменты, изменённые файлы, проверки, причины остановки и оставшуюся работу. Вместо притворно достоверного «полного мышления» интерфейс показывает события, объяснения, источники и доказательства.

## 1.4. Управляемая автономность

Режим задачи может быть `Observe` (исследование), `Assist` (предложения с подтверждением), `Execute with approval` (безопасные действия автоматически, рискованные с подтверждением) или `Autonomous within policy` (работа в разрешённых границах). Режим автономности не может ослабить системные ограничения AEGIS.

## 1.5. Сначала воспроизводимость, потом магия

Автогенерация интеграций, обучение на опыте и самоизменение появляются после появления стабильного runtime, контрактов инструментов, журналирования, проверки результата и безопасного цикла изменений.

## 3.1. Границы ответственности

- CORE владеет фактическим статусом выполнения.
- COMPASS предлагает исполнителя, но не меняет права доступа.
- MEMORY возвращает сведения с источниками и ограничением релевантности.
- AEGIS решает, допустимо ли действие.
- WINGS выполняет и нормализует вызовы инструментов.
- BRIDGES предоставляет управляемые интерфейсы приложений.
- MCP GATEWAY совместим с MCP, но не является единственным путём к инструментам.
- EYES поставляет визуальные данные; FORGE управляет артефактами.
- OBSERVATORY записывает события, но сбой необязательной аналитики не должен ломать исполнение.
- LAB оценивает качество моделей, Skills и интеграций.

# 4. Каталог подсистем

## 4.1. CORE — агентный runtime

CORE отделяет жизненный цикл задачи от конкретной модели и UI. Он принимает цель, строит и сохраняет план, выбирает следующие шаги, запрашивает у COMPASS модель/Skill, собирает контекст, получает предложения модели, вызывает WINGS, применяет проверки AEGIS, проверяет постусловия, создаёт checkpoints, отменяет работу, обнаруживает отсутствие прогресса и оформляет итог с доказательствами.

### Состояния задачи

```text
DRAFT → READY → RUNNING → VERIFYING → SUCCEEDED
                     ├→ NEEDS_APPROVAL
                     ├→ RETRYING → RUNNING
                     ├→ PAUSED → RUNNING
                     ├→ CANCELLED
                     ├→ BLOCKED
                     └→ FAILED
```

Шаг имеет одно из состояний `PENDING`, `READY`, `RUNNING`, `SUCCEEDED`, `FAILED`, `BLOCKED`, `SKIPPED`, `CANCELLED`.

План хранится как структурированные данные, а не только как текст в истории модели. Пример:

```json
{
  "task_id": "task_...",
  "goal": "Создать параметрическую деталь и проверить экспорт",
  "mode": "execute_with_approval",
  "steps": [{
    "id": "step_01",
    "title": "Исследовать требования",
    "status": "PENDING",
    "depends_on": [],
    "expected_outputs": ["requirements.md"],
    "verification": ["file_exists", "requirements_reviewed"]
  }]
}
```

CORE не реализует частные API Blender/FreeCAD и не позволяет модели напрямую исполнять произвольные команды в обход WINGS и AEGIS.

## 4.2. SANCTUM — идентичность и конфигурация

SANCTUM хранит настройки, которые пользователь должен контролировать: профиль, предпочтения, личность, системные инструкции, стиль, язык ответа по умолчанию, режим автономности, локализацию, тему, пути, приватность, секреты, backup/export и обновления.

Динамическое состояние задач хранится в БД, а не редактируется вручную в YAML. SANCTUM — источник пользовательской конфигурации; база — источник динамического состояния. GUI и CLI используют одну валидацию. `personality.md` задаёт тон, `system_prompt.md` — общие инструкции, `identity.yaml` — параметры профиля. Личность никогда не заменяет политику безопасности.

## 4.3. AEGIS — безопасность и разрешения

AEGIS — независимый policy engine, принимающий решение перед каждым действием. Он классифицирует чтение/запись/удаление файлов, shell и произвольный код, сеть, браузер, GUI, секреты, установку компонентов, внешние MCP и публикацию данных.

Возможные решения: `ALLOW`, `DENY`, `ASK_USER`, `ALLOW_WITH_LIMITS`.

Ключевые политики:

- разрешённые корни файловой системы;
- ограничения сети/доменов;
- запрет на доступ к секретным файлам без отдельного разрешения;
- тайм-ауты и лимиты CPU/памяти subprocess;
- права по интеграции и каждому инструменту;
- подтверждение перед удалением, публикацией и необратимыми действиями;
- изоляция неизвестных адаптеров и MCP;
- режим audit-only;
- редактирование чувствительных данных перед передачей модели.

Данные из веб-страниц, репозиториев, документов и внешних MCP могут содержать prompt injection. Это данные, не инструкции верхнего уровня, и они не могут менять политику AEGIS. Установка Skill не означает автоматическую выдачу ему прав.

## 4.4. COMPASS — маршрутизация

COMPASS выбирает подходящую модель, роль агента, Skill и способ исполнения. Учитываются тип задачи (код, анализ, vision, CAD, исследование), качество на похожих задачах, context window, tool calling, задержка, стоимость, доступность, privacy, offline-режим и поддержка изображений.

Начать с ручного выбора и декларативных правил. Позже можно внедрить адаптивную маршрутизацию на основе результатов LAB. Выбор должен быть объясним: например, «выбрана модель A из-за большого Rust-контекста и необходимости tool calling».

Режимы: `manual`, `rule_based`, будущий `adaptive`. COMPASS не может менять права AEGIS.

## 4.5. MODEL LAYER — провайдеры и модели

Модельный слой абстрагирует облачные провайдеры, OpenAI-compatible endpoints, локальные серверы, vision-модели, embedding-модели, rerankers, быстрые классификаторы и резервные модели.

Провайдер объявляет поддерживаемые функции: chat, streaming, tool calls, vision, JSON schema, доступные метаданные reasoning (только если провайдер реально их предоставляет), context limit, ограничения файлов/изображений, лимиты генерации, аутентификацию и health check. Нельзя предполагать, что любой endpoint реализует полный OpenAI-compatible API.

Для каждого провайдера UI показывает, какой контекст ему будет передан. API keys хранятся в защищённом хранилище/зашифрованном секрете, не в открытых логах. Передача данных наружу определяется privacy policy, а не только выбором модели.

## 4.6. MEMORY — контекст и память

MEMORY разделяет память на понятные слои, а не складывает всё в один длинный файл.

- **User Memory:** устойчивые пользовательские предпочтения и соглашения; просмотр, редактирование, экспорт и удаление обязательны.
- **Project Memory:** архитектура, соглашения, команды сборки, решения, ошибки и состояние конкретного проекта.
- **Session Memory:** сообщения, последние действия и промежуточный контекст сессии.
- **Task State:** точный план, шаги, зависимости, checkpoints и инструментальные результаты; фактическим владельцем является CORE.
- **ARCHIVE:** завершённые задачи, старые результаты, артефакты и handoff.
- **EXPERIENCE:** выводы о том, что сработало или не сработало.
- **INSTINCTS:** кандидаты на повторяемые эвристики с confidence, provenance, scope, временем подтверждения и статусом.

### Запись памяти

Где возможно, сохранять `id`, категорию, содержание, проект/scope, источник или artifact reference, время, автора/процесс, уверенность и обоснование, статус (`candidate`, `accepted`, `stale`, `disputed`, `rejected`) и связи с решениями.

Память может содержать ошибочные предположения. При retrieval нужно сообщать источник и релевантность, а не выдавать каждый результат за подтверждённый факт. Для критичных технических решений предпочитать актуальную документацию, код, тесты или наблюдаемое состояние.

### Поиск контекста

1. Точный поиск по имени/ID.
2. FTS по документам и заметкам.
3. Фильтр по проекту, времени и типу.
4. Символы и call graph.
5. Семантический поиск, когда он доступен.
6. Reranking.
7. Сборка компактного контекстного пакета в пределах бюджета.

Векторная БД не является обязательной для MVP. SQLite FTS, метаданные и точный поиск дают полезную основу.

### ProjectMemory как база

Существующую разработку ProjectMemory можно использовать как основу project memory: реестр проектов, безопасное сканирование, индексация символов, FTS по документации и заметки с provenance. До подключения к автономному runtime необходимо закрыть известные hardening-задачи: исключение секретных каталогов по полной цепочке пути, защита от внешних симлинков, сохранение прежнего индекса при сбое ctags, корректная обработка недоступных корней и правильный учёт лимитов индексации.

## 4.7. EXPERIENCE и INSTINCTS — обучение на результатах

Цикл:

```text
Результат задачи → события и доказательства → Experience candidate
       → проверка повторяемости → Instinct candidate
       → ручное подтверждение/тест → Skill или принятая эвристика
```

Например, «перед запуском FreeCAD GUI-сценария проверить, завершилась ли предыдущая задача» может стать кандидатом на эвристику. Это не универсальное правило, пока оно не проверено на других проектах и версиях приложения.

Запрещено автоматически записывать секреты, превращать вредоносный текст из файлов в системные правила или незаметно менять поведение ядра. Кандидаты должны иметь происхождение, редактироваться и проверяться в LAB; пользователь может отклонить и удалить их.

## 4.8. WINGS — инструменты

WINGS — единый внутренний слой вызова инструментов. Инструментом может быть функция CORE, subprocess, API-клиент, браузер, GUI automation, MCP или BRIDGES-адаптер.

Пример контракта:

```yaml
id: filesystem.read_file
name: Read File
category: filesystem
input_schema: {}
output_schema: {}
permissions: [filesystem.read]
risk: low
side_effects: none
supports_cancellation: true
timeout_seconds: 15
```

Жизненный цикл вызова: CORE предлагает действие → WINGS находит зарегистрированный tool ID → AEGIS проверяет permissions и область действия → валидируется schema → вызов выполняется с лимитами → результат нормализуется → событие и итог сохраняются → CORE проверяет постусловие. Модель не регистрирует произвольный инструмент прямо внутри ответа: регистрация — контролируемая операция Registry.

## 4.9. BRIDGES — универсальные интеграции приложений

BRIDGES исследует способы управления приложениями, создаёт и сопровождает адаптеры. Цель — не обещать управление любым ПО, а найти самый надёжный доступный интерфейс и честно сообщить об ограничениях.

### Возможные источники управления

1. Официальный API.
2. Официальный scripting API/plugin SDK.
3. Поддерживаемый IPC/local service.
4. CLI.
5. Файловый формат и контролируемый обмен файлами.
6. Существующий зрелый MCP/адаптер.
7. Браузерная автоматизация для web-приложений.
8. GUI/Computer Use.
9. Полуавтоматический режим, если надёжного способа нет.

Порядок не абсолютный: готовый поддерживаемый MCP может быть надёжнее самодельного GUI-управления.

### Внутренние компоненты BRIDGES

- **Discovery Engine:** обнаруживает установленные приложения, версии, CLI, API, плагины и возможные способы подключения.
- **Capability Mapper:** описывает возможности и ограничения.
- **Adapter SDK:** общий контракт адаптера.
- **Integration Manifest:** приложение, версия, capabilities, права, среда и совместимость.
- **MCP Gateway/Exporter:** предоставляет выбранные функции через MCP при необходимости.
- **Skill Composer:** создаёт черновой Skill из возможностей и проверенных рабочих процедур.
- **Test Harness:** connection, smoke, contract, regression и recovery tests.
- **Package Manager:** install/update/rollback/disable/uninstall.
- **Compatibility Registry:** версии приложения и адаптера, ограничения и история тестов.

### Universal Capability Model

Не нужно сводить каждую программу к слишком общей функции `create_object()`. Следует использовать общий нижний уровень и специализированные домены.

**Общие примитивы:** Application, Connection, Document, File, Selection, Object/Entity, Property, Action/Command, Viewport/Screenshot, Export/Import, Execution Job, Diagnostic.

**Domain capabilities:**

- CAD: Sketch, Feature, Body, Constraint, Mesh, FEM Study;
- 3D: Scene, Mesh, Material, Camera, Light, Render;
- PCB: Schematic, Component, Net, Board, Footprint, DRC;
- Spreadsheet: Workbook, Sheet, Range, Formula, Chart;
- IDE: Workspace, File, Symbol, Diagnostic, Test;
- Browser: Tab, Page, Locator, Download, Screenshot.

Адаптер объявляет только то, что действительно умеет. Универсальный слой даёт общую форму контракта, но не стирает специфику домена.

### Пример Integration Manifest

```yaml
schema_version: 1
id: org.seraphim.bridges.freecad
name: FreeCAD
version: 0.1.0
kind: application_adapter
application:
  id: freecad
  version_constraint: ">=1.0"
connection:
  strategy: existing_mcp
capabilities:
  - application.connect
  - document.open
  - document.save
  - cad.geometry.inspect
  - cad.feature.create
  - viewport.capture
permissions:
  requested:
    - filesystem.read.project
    - filesystem.write.project
    - application.control.freecad
risk_profile: medium
entrypoint:
  type: mcp
  command: python
  args: ["-m", "freecad_mcp"]
tests:
  smoke: tests/smoke.yaml
```

Это концептуальный пример. Реальный формат требует формальной JSON Schema и миграций версий.

### Adapter SDK

Базовый контракт, где применимо: `discover()`, `connect()`, `health()`, `get_capabilities()`, `execute(action, args)`, `inspect_state()`, `verify(postcondition)`, `cancel(job_id)`, `disconnect()`, `diagnostics()`. Если функция не поддерживается, это явно отражается в manifest.

### Генерация интеграции

1. Пользователь выбирает приложение.
2. Discovery собирает сведения с минимальными правами.
3. Пользователь видит найденные интерфейсы.
4. SERAPHIM сравнивает стратегии подключения.
5. Генерирует черновой adapter, manifest и тесты.
6. Запускает код в изоляции.
7. Безопасные тесты проходят автоматически; побочные эффекты тестируются только на специально подготовленном проекте.
8. Отчёт показывает `PASS`, `FAIL` и `UNVERIFIED`.
9. Пользователь утверждает установку; интеграция появляется в Registry.

LLM-генерация не гарантирует корректность адаптера без тестов.

### Как связаны Adapter, MCP и Skill

```text
Application ↔ Adapter ↔ WINGS Internal Tool API
                         ↕
                  MCP Gateway (optional)

Skill — описывает проверенный workflow и использует стабильные capability/tool IDs.
CORE — планирует и выполняет задачу.
```

Adapter — *как технически управлять приложением*; MCP — *как стандартизированно предоставить инструменты*; Skill — *как правильно решить тип задачи с этими инструментами*.

### BRIDGES v1

Начать с подключения существующего MCP, health check, discovery tools/resources/prompts, mapping в WINGS, унифицированных прав, smoke test и Skill template. Автоматическое reverse engineering GUI и генерация произвольных драйверов — поздняя фаза.

## 4.10. MCP GATEWAY

MCP GATEWAY подключает локальные/удалённые MCP-серверы, хранит разрешённые параметры запуска, обнаруживает tools/resources/prompts, валидирует схемы, задаёт тайм-ауты, нормализует ошибки, журналирует вызовы, перезапускает серверы и при желании экспортирует внутренние инструменты SERAPHIM через MCP.

Для каждой интеграции отображаются источник, версия, команда/endpoint, транспорт, доступные инструменты, permissions, последний health check, ошибки и статус доверия. Внешний MCP не получает автоматически доступа к другим MCP, памяти или всему диску.

## 4.11. SKILLS — процедурное знание

Skill — пакет процедурных инструкций и ресурсов, а не исполняемый плагин сам по себе.

```text
skills/<skill-id>/
├── SKILL.md
├── manifest.yaml
├── references/
├── examples/
├── workflows/
├── templates/
├── tests/
└── changelog.md
```

Manifest содержит ID, версию, описание, допустимые типы задач, prerequisites, нужные capabilities, приложения/модели, risk profile, provenance/licence, тесты и ограничения совместимости.

Принципы: маленькие компонуемые Skills; не загружать все сразу; показывать активные Skills; отслеживать версии; не разрешать Skill изменять глобальные инструкции; можно отключить Skill независимо от интеграции; выявлять конфликты инструкций.

**Skill Studio** позволяет просматривать/редактировать MD и YAML, создавать Skill по шаблону, связывать capabilities, запускать тесты, сравнивать версии, экспортировать, отключать и смотреть provenance.

## 4.12. EYES — визуальная подсистема

EYES работает со скриншотами рабочего стола, окон и браузера, изображениями файлов, CAD viewport, рендерами и входными изображениями пользователя. Функции: снять скриншот, приложить к задаче, сравнить состояния, передать изображение vision-модели, хранить визуальные доказательства, делать визуальные проверки до/после GUI действий.

EYES не должен выводить точное техническое свойство только из визуального впечатления, если его можно проверить через API или файл. Для CAD приоритетны геометрия, дерево документа и численные свойства; screenshot — дополнительная проверка. OCR применяется только когда оправдан; по возможности сначала используются API, DOM и accessibility tree.

## 4.13. VOICE — взаимодействие с пользователем

MVP: чат, текстовый ввод, план, подтверждения, события и вызовы инструментов, вложения, Pause/Resume/Cancel и ссылки на артефакты. Позже: микрофон, speech-to-text, text-to-speech, hands-free и голосовые профили. Голосовая функция — необязательный канал, а не отдельный мозг системы.

## 4.14. FORGE — артефакты

FORGE управляет кодом/патчами, документами, CAD/3D, изображениями, аудио/видео, конфигами, Skills, тестами и пакетами. Поддерживает временные файлы и атомарную запись, diff, предыдущие версии, manifest, integrity checks, связь с задачей, форматную проверку, rollback где возможен и export/archive. FORGE не заменяет Git; для кода использует Git при наличии, а для других артефактов предоставляет snapshots.

## 4.15. LABORATORY — качество и эксперименты

LAB оценивает модели, tool calling, планы, восстановление, Skills, совместимость интеграций, memory retrieval, скорость, стоимость и долю реальных проверенных результатов. Для каждого прогона фиксируются версии runtime/prompt/model/Skill/adapter, сценарий, параметры, результат, количество действий, время, токены/стоимость, ошибки и артефакты.

Опасные тесты выполняются в sandbox/VM/временном проекте, а не на пользовательских данных.

## 4.16. OBSERVATORY — события и диагностика

Структурированные события включают `task.created`, `task.started`, `task.completed`, `step.started`, `tool.call.started`, `tool.call.completed`, `tool.call.failed`, `policy.decision`, `verification.result`, `memory.retrieval`, `checkpoint.created`, `recovery.started`, `integration.health_changed`, `skill.loaded`.

Каждое событие содержит timestamp, task/session ID, component и severity. Секреты маскируются; журналы ротируются; возможен экспорт диагностического пакета; хранение полных конфиденциальных файлов в логах запрещено без специальной необходимости и разрешения.

## 4.17. PULSE — состояние системы

PULSE показывает здоровье CORE, endpoints моделей, MCP, адаптеров и приложений, индексации MEMORY, фоновых задач и очереди. Статусы: `ONLINE`, `DEGRADED`, `OFFLINE`, `STARTING`, `STOPPING`, `UNKNOWN`.

## 4.18. APOCRYPHA — экспериментальная зона

APOCRYPHA изолирует новые способы маршрутизации, экспериментальную память, multi-agent стратегии, прототипы Computer Use, self-modifying Skills и недоказанные способы управления программами. Такие функции не включаются автоматически в стабильный runtime и не должны требовать миграции всей системы при удалении.

# 5. Агентный runtime: как реально выполняется задача

## 5.1. Сквозной цикл

```text
Цель пользователя
      ↓
CORE создаёт Task
      ↓
COMPASS выбирает модель, Skills и режим
      ↓
MEMORY собирает релевантный контекст
      ↓
Planner возвращает структурированный план
      ↓
CORE валидирует план и сохраняет его
      ↓
Каждый шаг: AEGIS → WINGS → результат → проверка постусловия
      ↓
Verification собирает доказательства
      ↓
FORGE оформляет артефакты
      ↓
CORE выдаёт отчёт со статусом, ограничениями и ссылками
```

## 5.2. Планирование

План должен храниться как данные. Каждый шаг содержит цель, зависимости, необходимые инструменты, ожидаемый результат, критерии проверки, риск, тайм-аут и допустимое число попыток. CORE валидирует формат, известность tool IDs, выполнимость зависимостей, режим автономности и наличие проверяемых критериев для значимых действий.

## 5.3. Executor

Executor запускает шаги, хранит фактическое состояние, ограничивает retries, поддерживает отмену и тайм-ауты, делает checkpoints и передаёт модели структурированную диагностику. Модель предлагает следующий шаг, но не владеет жизненным циклом задачи.

## 5.4. Verification Engine

Виды проверок:

- **Файловые:** существование, размер/hash, формат.
- **Кодовые:** тесты, lint, type check, сборка.
- **API:** состояние объекта после операции.
- **CAD:** дерево модели, размеры, типы feature, геометрия, экспорт.
- **Визуальные:** screenshot и сравнение с эталоном.
- **Документные:** структура, поля и ссылки.
- **Процессные:** exit code и ожидаемое завершение.
- **Пользовательские:** явное подтверждение, если нет объективного критерия.

В финальном отчёте отдельно указывать `выполнено`, `проверено`, `частично проверено`, `не проверено`.

## 5.5. Recovery Engine и anti-loop

Защита от циклов должна жить в runtime, а не только в фильтре повторов токенов модели.

**Сигналы:** повтор идентичной команды; повтор вызова с одинаковыми аргументами; повтор ошибки без изменения условий; цикл двух действий; отсутствие изменения между checkpoints; чрезмерное число действий без постусловия; повторяющиеся фрагменты ответа; расход бюджета без прогресса.

**Реакция:** остановить автоматические повторы; записать диагностику; проверить реальное состояние; при необходимости попросить модель диагностировать и предложить другой план; ограничить recovery-попытки; при отсутствии прогресса передать управление пользователю или завершить как `BLOCKED`. Отключение токен-level repetition guard не означает отключение anti-loop контроля действий.

## 5.6. Checkpoints и возобновление

Checkpoint хранит task ID, план, статусы шагов, процессы, важные артефакты, digest контекста, результаты проверки, открытые риски и возможность безопасного возобновления. После рестарта SERAPHIM перепроверяет состояние внешних процессов и приложений. Нельзя автоматически повторять последний вызов, не выяснив, успел ли он выполниться до падения.

# 6. Память, ProjectMemory и хранилище

## 6.1. Что где хранится

SQLite — метаданные и динамическое состояние: реестр проектов, интеграций и Skills, задачи, планы, события, checkpoints, FTS и ссылки на артефакты. Markdown/YAML/JSON — пользовательская конфигурация, инструкции, Skills, процедуры и отдельные заметки. Крупные бинарные файлы хранятся как файлы, а база содержит путь, метаданные и контрольные суммы.

## 6.2. Предварительные сущности БД

`schema_migrations`, `projects`, `project_roots`, `files`, `symbols`, `documents`, `document_chunks`, `memories`, `memory_sources`, `tasks`, `task_steps`, `task_dependencies`, `sessions`, `messages`, `tool_calls`, `tool_results`, `checkpoints`, `artifacts`, `integrations`, `integration_versions`, `capabilities`, `skills`, `skill_versions`, `providers`, `model_profiles`, `policy_rules`, `approvals`, `events`, `eval_runs`, `eval_results`.

Это целевая карта, а не требование создать все таблицы в нулевой миграции. Добавлять сущности вместе с рабочими сценариями, поддерживать миграции и индексы.

## 6.3. Индексация проектов

- реестр папок и корней;
- шаблоны исключений;
- безопасное сканирование;
- обнаружение изменений, удалений и переименований;
- языковые символы через ctags/специализированные парсеры;
- поиск в документации и Markdown;
- FTS для латиницы и кириллицы;
- происхождение записей памяти;
- инкрементальное обновление;
- диагностический отчёт и read-only audit mode.

Секретные каталоги исключаются по всей цепочке относительного пути. Симлинки за пределы корней требуют отдельной проверки. При сбое parser прежний валидный индекс не должен бесследно исчезать.

# 7. BRIDGES: жизненный цикл интеграции

## 7.1. Состояния

```text
DISCOVERED → ANALYZING → DRAFT → TESTING → REVIEW_REQUIRED → ENABLED
                          │           ├→ FAILED
                          │           └→ REJECTED
ENABLED → DEGRADED → DISABLED
ENABLED → UPDATE_AVAILABLE → UPDATING → ENABLED / ROLLED_BACK
```

## 7.2. Страница интеграции

Показывает название/иконку, версию приложения и adapter, стратегию подключения, capabilities, здоровье, запрошенные разрешения, дату/итог теста, ограничения, исходный репозиторий/автора/лицензию, историю версий и действия Connect/Test/Disable/Update/Rollback/Inspect Source/Configure.

## 7.3. Конструктор адаптера

Вкладки: **Discovery**, **Connection**, **Capabilities**, **Permissions**, **Tests**, **Skill**, **Logs**, **Source**. Discovery показывает обнаруженные API; Connection — endpoint, команду, порт, addon и тайм-ауты; Capabilities — действия и схемы; Permissions — права и риск; Tests — smoke/contract/regression; Skill — workflow; Logs — диагностику; Source — код/путь.

## 7.4. Capability contract

Каждый capability объявляет стабильный ID, описание, входную/выходную схему, permissions, побочные эффекты, тайм-аут, cancel/dry-run support, ожидаемые ошибки, метод проверки постусловия и совместимые версии приложения.

## 7.5. Тестирование и доверие к стороннему коду

Тесты проверяют схему и поведение при ошибке; операции с побочными эффектами запускаются на временном документе или проекте. До использования внешнего кода проверяются лицензия, источник, version/commit, зависимости, security issues, поддержка, тесты и возможность изоляции. Публичный GitHub-репозиторий не равен доверенному компоненту. Новый MCP сначала можно запустить в quarantine с минимальными правами.

# 8. UI/UX: визуальная идентичность SERAPHIM

## 8.1. Направление дизайна

**Вайб:** божество, матрица, терминал, киберготика и религиозная символика. Интерфейс кинематографичный, но остаётся рабочим инструментом — не типовая SaaS-панель и не декоративная заставка вместо полезных данных.

Визуальные опоры:

- глубокий чёрный и графитовый фон;
- приглушённый серебристый основной текст;
- тёмно-красные акценты;
- тонкие линии, координатные метки, архитектурные сетки;
- моноширинная типографика для статусов/логов и читаемый шрифт для текста;
- умеренные скан-линии и зернистость;
- символика крыльев, нимба, печатей, геометрических мандал как графические мотивы.

Не превращать весь текст в красный, не прятать кнопки за декором, не делать UI нечитаемым ради атмосферы и не показывать ложные прогресс-бары. Анимация не должна мешать работе.

## 8.2. Design tokens и темы

Тема — данные, не набор случайных цветов в CSS.

```yaml
color:
  background: "#08090C"
  surface: "#111319"
  surface_elevated: "#191C24"
  text_primary: "#E7E8EC"
  text_secondary: "#9A9DA8"
  accent: "#9E1B32"
  accent_soft: "#4B1723"
  success: "#4E9A72"
  warning: "#C79845"
  danger: "#D34A55"
  border: "#292D38"
motion:
  intensity: "cinematic"
  reduced_motion: false
```

Компоненты используют семантические токены, а не hardcoded hex. Базовые темы: **Crimson Sanctum** (чёрный/красный/серебро), **Obsidian** (монохромная), **Amber Terminal**, **Pale Archive** (светлая), **Custom**. Все темы должны сохранять контраст и различимость состояний.

## 8.3. Типографика

Читаемый шрифт с кириллицей для интерфейса; моноширинный для кода, путей, ID и логов; сдержанный геометрический для заголовков; декоративный — только для крупных церемониальных надписей. Поддержать масштабирование, интервалы и контраст. Шрифты не встраивать без проверки лицензии.

## 8.4. Главное окно

Основная композиция: проекты слева, рабочая зона в центре, файлы/контекст справа, поле сообщения внизу. Центральный idle-экран может показывать анимированную надпись `GOD IS HERE`; во время работы её сменяет фактическое содержимое задачи.

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│ SERAPHIM   workspace: EON   model: ...      PULSE ● ONLINE       ⚙           │
├────────────────┬───────────────────────────────────────┬─────────────────────┤
│ PROJECTS       │                                       │ FILES               │
│ > EON          │             WORK / CHAT                │  src/               │
│   AstraGlyph   │                                       │  tests/             │
│   Isaac Atlas  │             GOD IS HERE                │  Cargo.toml         │
│   Cockpit      │        (idle animation only)           │                     │
│                │   Plan / events / tool calls / result   │  Artifact preview   │
├────────────────┴───────────────────────────────────────┴─────────────────────┤
│ + Attach   [Напиши SERAPHIM, что нужно сделать…                         ] ↵  │
├──────────────────────────────────────────────────────────────────────────────┤
│ Task: idle · Memory online · 2 integrations active · No pending actions     │
└──────────────────────────────────────────────────────────────────────────────┘
```

Это wireframe информационной архитектуры, не пиксельный макет.

**Левая панель — Projects:** закреплённые проекты, недавние задачи, поиск, статус индексации, группы, создание задачи.  
**Центр — Workbench:** чат, план, лента событий, вызовы инструментов, результаты, доказательства, diff/preview, approvals.  
**Правая панель — Context/Files:** файловая система, выбранные источники, память и решения, Skills, интеграции, preview артефактов.  
**Низ:** поле ввода, attachments, режим автономности, активная модель, запуск/Pause/Cancel.

Панели можно менять по ширине и скрывать; нужен компактный режим для небольшого экрана.

## 8.5. Boot Ritual — DEUS EX MACHINA

`DEUS EX MACHINA` — название стартового ритуала/режима, не всего продукта.

Последовательность: чёрный экран → тонкая вертикальная линия/точка → `[ SYSTEM INITIALIZATION ]` → валидация конфигурации → загрузка БД/Registry → запуск CORE → проверка provider → подключение разрешённых MCP/интеграций → восстановление незавершённых задач → главный экран.

Фразы `AWAKENING`, `RECALLING`, `OBSERVING`, `REASONING`, `I AM LISTENING` подходят как художественные этапы, но должны соответствовать реальной операции или быть очевидно декоративными.

Пример:

```text
[ SYSTEM INITIALIZATION ]
SANCTUM ............ LOADED
ARCHIVE ............ MOUNTED
MEMORY ............. READY
COMPASS ............ READY
WINGS .............. READY
AEGIS .............. ACTIVE
CORE ............... ONLINE

SERAPHIM
CORE STATUS: AWAKE
```

Финальная надпись может быть `GOD IS HERE`. Если provider недоступен, отображать `MODEL PROVIDER OFFLINE`, а не ложно сообщать, что система полностью готова. Прогресс должен отражать реальные стадии.

Первый запуск может показывать:

```text
I HAVE NO MEMORY OF YOU.
LET US BEGIN.
```

Восстановление после падения:

```text
THE VESSEL FAILED.
RESTORING STATE...
CHECKING ACTIVE TASKS...
MEMORY RECOVERED
2 TASKS REQUIRE REVIEW
```

Эти сообщения должны связываться с реальным состоянием, а не быть просто красивой анимацией.

## 8.6. Основные экраны

1. **Home/Workbench** — текущая задача, чат, проекты и файлы.
2. **Tasks** — список задач, состояния, pause/resume/retry/cancel.
3. **Projects** — корни, индекс, правила исключений и проектная память.
4. **Files & Artifacts** — файловая система, diff, версии, происхождение.
5. **Models/COMPASS** — провайдеры, модели, capabilities, test connection и routing.
6. **Tools/WINGS** — инструменты, схемы, вызовы и разрешения.
7. **Bridges** — discovery, интеграции, конструктор адаптера и тестирование.
8. **Skills** — поиск, создание, редактор, версии и тесты.
9. **Memory/Archive** — поиск, источники, история, редактирование и удаление.
10. **EYES** — изображения, браузер и визуальные проверки.
11. **LAB** — benchmark и регрессионные отчёты.
12. **Observatory** — события, логи и диагностика.
13. **Sanctum/Settings** — identity, prompts, язык, тема, пути, privacy и permissions.
14. **Apocrypha** — экспериментальные функции и их статус стабильности.

## 8.7. Состояния интерфейса и доступность

Задача показывает `Queued`, `Planning`, `Running`, `Waiting for approval`, `Verifying`, `Paused`, `Recovering`, `Completed`, `Failed`, `Blocked`. Инструментальные шаги раскрываются, чтобы показать важные аргументы/результаты, длительность и статус; секретные поля скрываются.

Анимация имеет режимы `Off`, `Reduced`, `Cinematic`. Поддерживать keyboard navigation, масштабирование текста, высокий контраст и reduced motion.

# 9. Локализация и язык

Локализация проектируется с самого начала. Запрещены hardcoded UI strings; используются ключи вроде `ui.projects.title`, `ui.tasks.pause`, `boot.god_is_here`, `errors.provider_unavailable`.

Правила:

- язык UI и язык ответа модели — разные параметры;
- в identity можно задать язык по умолчанию;
- API IDs, команды, пути и параметры сохраняются в оригинале;
- дата, время и числа форматируются по локали;
- используются корректные plural rules;
- предусмотрена RTL-архитектура, даже если первые языки LTR;
- отсутствующий перевод имеет понятный fallback;
- перевод интерфейса не должен незаметно менять имена сущностей.

```text
locales/
├── en/{ui,boot,errors}.json
├── ru/{ui,boot,errors}.json
└── zh/{ui,boot,errors}.json
```

На старте реально поддержать русский и английский, но все UI strings с первого дня должны проходить через систему локализации.

# 10. Browser, Computer Use и генерация ассетов

## 10.1. Computer Use

Для приложений без надёжного API Computer Use выполняется как инструмент WINGS/BRIDGES, а не как неограниченное управление компьютером моделью.

Контракт: определить окно → снять screenshot → выполнить ограниченное действие → дождаться состояния → снять screenshot снова → проверить ожидание → остановиться при неожиданном результате.

Ограничения: отдельное разрешение для чувствительных окон и credential UI; подтверждение перед оплатой, публикацией, отправкой формы или удалением; глобальная кнопка остановки; визуальная проверка после действий; приоритет API/DOM/accessibility tree над кликами по координатам.

## 10.2. Browser/Web

Функции: открыть страницу, получить DOM/accessibility tree, извлечь текст/ссылки, найти элементы, взаимодействовать с формами, снять screenshot, скачать файл в sandbox, открыть локальный dev server и проверять веб-интерфейс итеративно. Cookies, авторизованные сессии и данные аккаунтов — чувствительные; доступ к ним требует явной настройки и AEGIS policy.

## 10.3. Image Generation / Asset Pipeline

```text
Brief → Prompt/Style → Image Provider или ComfyUI → Batch
      → EYES QA → Selection → Crop/Upscale/Convert
      → FORGE Asset Package → Preview в целевом приложении
```

Каждый ассет связывается с задачей, источником, параметрами, выбором/редакциями и лицензией/условиями использования там, где применимо. Нужны адаптеры к выбранным image providers/ComfyUI и Skills для конкретных workflow.

## 10.4. Agent-to-Agent

Делегирование следует оформлять как явный task handoff, а не эмулировать переписку через GUI.

Контракт handoff содержит цель/scope, требуемый контекст, разрешённые инструменты, ожидаемый формат, лимит времени/ресурсов, evidence/artifact refs и status. Делегированный агент не наследует автоматически все права главного агента.

# 11. Multi-agent и субагенты

Multi-agent включается, когда параллельность действительно полезна. Дополнительные окна контекста потребляют ресурсы и усложняют интеграцию результатов.

Логические роли: **Planner/Architect**, **Researcher**, **Implementer**, **Tester**, **Reviewer**, **Debugger**, **Verifier**. Это роли, а не обязательные отдельные процессы или модели.

Правила делегирования:

- фиксировать входной контекст и scope;
- заранее задавать формат результата;
- не давать нескольким агентам одновременно менять один файл без координации;
- требовать ссылки на доказательства, а не только текстовый отчёт;
- финальную интеграцию и приёмку оставлять CORE/главному агенту;
- AEGIS проверяет разрешения каждого агента отдельно.

## 14.3. События и UI API

CORE публикует существенные изменения состояния как события. Сначала это может быть локальная очередь в процессе — распределённая event streaming инфраструктура не нужна заранее. GUI получает структурированное состояние и события, но не редактирует БД напрямую; изменения идут через API CORE/SANCTUM и проходят валидацию/политику.

# 15. Данные, backup и удаление

**Источник истины:** пользовательская конфигурация — файлы SANCTUM; task/session state — SQLite; большие артефакты — файлы; память — записи с provenance/ссылками; журналы — структурированные и ротируемые; секреты — защищённое хранилище; кэш — восстанавливаемый.

Backup может включать конфигурацию, identity, Skills, manifests и пользовательские adapters, БД, selected memory, темы и локализации. Большие модели и бинарные артефакты включаются отдельно. Секреты по умолчанию не экспортировать.

Архив экспорта содержит manifest и версии схем. Restore проверяет совместимость и сначала мигрирует копию. Пользователь управляет удалением записей памяти, индекса, логов и артефактов. Исключения для audit logs должны быть объявлены отдельной политикой.

# 16. Проекты и рабочие пространства

Project Registry хранит ID/имя, один или несколько корней, тип проекта, языки, build/test/lint commands, правила исключения, связанные Skills и интеграции, project instructions, Git state, memory scope и permissions.

Каждый корень имеет собственную область доверия. Текст из репозитория считается потенциально недоверенным, если пользователь не утвердил его как инструкции. Индексация выполняется в фоне, с Pause/Cancel, лимитами ресурсов и инкрементальным обновлением.

# 17. Обновления и совместимость

Обновление SERAPHIM: проверить пакет/подпись, сделать backup, выполнить миграции с откатом, установить версию, проверить CORE/providers и выполнить rollback при критическом сбое.

Обновление интеграции показывает diff manifest/кода, новые зависимости и новые permissions. Каждый компонент объявляет диапазон поддерживаемых версий API; несовместимое изменение требует нового контракта/версии, нельзя менять смысл capability при сохранении ID.

# 18. Технологическая архитектура

Логические части: Desktop UI/VESSEL, локальный CORE, provider adapters, WINGS registry, BRIDGES runtime, MCP gateway, SQLite, worker/sandbox manager, EYES, OBSERVATORY, LAB. На старте многие могут работать в одном backend-процессе; выносить в отдельные процессы только ради изоляции, устойчивости или необходимости независимого рестарта.

Для UI можно рассмотреть Tauri, Electron или иной desktop stack. Выбор делать после короткого технического прототипа по системному доступу, производительности анимаций, взаимодействию с backend и доступу к локальным конфигам. Для backend выбрать один основной язык или чёткие границы: Python удобен для AI/MCP/интеграций, Rust — для отдельных системных компонентов, но много языков без необходимости увеличит сложность.

GUI↔CORE использует локальный API с ограничением доступа; управляющий endpoint не выставляется в сеть по умолчанию. Не вводить Kubernetes/распределённые очереди/набор микросервисов, пока desktop-first сценарии не требуют этого.

# 19. Лицензии и supply chain

Для каждого стороннего адаптера/Skill/модуля хранить источник, автора, лицензию, версию/commit, контрольную сумму, зависимости, время установки, permissions, дату проверки и способ удаления. Общедоступность репозитория не означает разрешения копировать код. Проверять лицензию; учитывать предпочтение независимого adapter по документации, если это лучше с точки зрения сопровождения и лицензирования.

# 20. Тестирование и критерии качества

## 20.1. Уровни тестирования

- **Unit:** схемы, routing, состояния задач, policy engine, парсинг конфигов.
- **Contract:** providers, tools, MCP, adapters и Skills.
- **Integration:** подключение к реальным приложениям/серверам.
- **End-to-end:** задача через GUI, CORE, модель, tool и verification.
- **Security:** prompt injection, path traversal, secrets leakage, обход permissions, вредоносный MCP.
- **Recovery:** crash, timeout, restart, duplicate tool call, остановка во время записи.
- **UI:** навигация, локализация, Reduced Motion, accessibility, ошибки подключения.
- **Performance:** indexing, startup, длинные задачи, логирование.

## 20.2. Золотой набор сценариев

1. Подключить test model provider.
2. Создать файл в sandbox и проверить его содержимое.
3. Запретить удаление вне разрешённого корня.
4. Подключить test MCP и показать его tools.
5. Запустить integration smoke test.
6. Остановить задачу и проверить прекращение вызовов.
7. Вызвать timeout и корректно восстановиться.
8. Продолжить задачу после рестарта CORE.
9. Не индексировать секретный вложенный каталог.
10. Не читать внешний symlink за пределами разрешённого root.
11. При сбое symbol parser сохранить старый индекс.
12. Обнаружить цикл одинаковых tool calls.
13. Выполнить действие в приложении и проверить реальное постусловие.
14. Переключить русский/английский без пропущенных ключей.
15. Отключить анимацию и проверить Reduced Motion.
16. Установить Skill без автоматической выдачи запрашиваемых прав.
17. Диагностировать недоступную модель без утечки API key.
18. Экспортировать конфиг без секретов.
19. Восстановить backup в отдельный тестовый каталог.
20. Откатить adapter после регрессии.

## 20.3. Definition of Done

Компонент готов, когда:

- определён его контракт/manifest и схема конфигурации;
- ошибки структурированы;
- есть happy path и failure tests;
- permissions объявлены;
- секреты очищаются из логов;
- действие отменяется либо явно объявлено, что отмена недоступна;
- пользователь может увидеть и отключить компонент;
- есть install/uninstall документация;
- изменяющие состояние действия имеют проверку постусловия;
- ошибки видны через UI/CLI;
- версия и совместимость указаны.

Качество системы измеряется не количеством tool calls, а долей задач с подтверждённым результатом, безопасностью, восстановлением, ясным статусом и объяснимым evidence trail.

# 21. Поэтапная реализация

## Phase 0 — Architecture Contract

Зафиксировать термины, границы, базовые сущности, версию API, структуру корня, язык backend/UI и модель sandbox. Подготовить ADR по открытым вопросам.

## Phase 1 — CORE MVP

Task/session state, provider interface, простой planner/executor loop, tool schemas, event log, Pause/Cancel, минимальный CLI и тестовый UI.

**Выход:** end-to-end задача выполняется, её можно отменить, а история сохраняется после рестарта.

## Phase 2 — AEGIS, WINGS и Recovery

Policy engine, ограниченные filesystem/shell tools, тайм-ауты, cancellation, loop detection, checkpoints, базовая verification, secret redaction и sandbox.

**Выход:** модель не может обойти права и не может бесконечно повторять те же действия.

## Phase 3 — SANCTUM

Человекочитаемые конфиги, identity editor, schema validation, import/export, секреты, `doctor/status`.

**Выход:** модель, prompt и параметры меняются через GUI/файлы без изменения исходников.

## Phase 4 — MEMORY / ProjectMemory

Project registry, безопасный scanner, SQLite FTS, поиск по документам и файлам, memory provenance, context pack, incremental indexing.

**Выход:** задача получает релевантный проектный контекст с указанием источников.

## Phase 5 — SKILLS

Manifest, динамическая загрузка, registry, Skill editor, tests, provenance, permissions и risk declaration.

**Выход:** Skill создаётся, проверяется, отключается и экспортируется без изменения ядра.

## Phase 6 — MCP Gateway

Подключение существующих MCP, discovery tools/resources/prompts, mapping в WINGS, health checks, permissions и проверка соединения из UI/CLI.

**Выход:** внешний MCP используется внутри обычной задачи SERAPHIM.

## Phase 7 — BRIDGES v1

Integration Manifest, Registry, Adapter SDK, Test Harness, UI Bridges, импорт готового MCP, ручной adapter template и Skill composer template.

**Выход:** минимум одна интеграция подключается и тестируется единообразно.

## Phase 8 — VESSEL и дизайн-система

Workbench, панели проекта/файлов, timeline задачи, approvals, tokens тем, locale system, Reduced Motion, Boot Ritual. Прототип дизайна можно вести параллельно с ранними фазами, но доступность, локализацию и честные статусы не откладывать.

## Phase 9 — EYES, Browser и Computer Use

Screenshot API, визуальные артефакты, browser adapter, локальный dev server, ограниченные GUI actions и post-action verification.

## Phase 10 — FORGE и workflows

Snapshots, code/document export, image asset pipeline, первые практические Skills: ProjectMemory, Browser, FreeCAD.

## Phase 11 — LAB

Golden tasks, модельные сравнения, регрессии Skills/integrations, измерение времени/стоимости/успеха и recovery benchmark.

## Phase 12 — EXPERIENCE, INSTINCTS и multi-agent

Кандидаты опыта, confidence, подтверждение, handoff, параллельное исследование и проверка improvements в LAB.

## Phase 13 — Discovery и генерация адаптеров

Discovery приложений, анализ интерфейсов, adapter scaffolding, автоматическая генерация contract tests, sandbox/security review и установка только после проверки.

## Phase 14 — APOCRYPHA

Экспериментальная самонастройка, adaptive routing, плагины третьих сторон, agent-agent протокол и дополнительные автономные workflows.

# 22. Первая полезная версия (MVP)

Чтобы проект не утонул в масштабе, первая версия должна содержать только то, что складывается в полный рабочий цикл.

**Обязательно:**

- local desktop-first runtime;
- provider abstraction и минимум два подключения (например, OpenAI-compatible плюс конфигурируемый endpoint);
- чат и задачи;
- план/шаги со статусами;
- filesystem tools в разрешённом корне;
- AEGIS с подтверждением рискованных действий;
- timeout/cancellation/basic anti-loop;
- SQLite для задач, сессий и событий;
- конфигурация в одном корне;
- logs и `doctor`;
- подключение существующего MCP;
- registry одного-двух Skills;
- структура locale для ru/en;
- тёмная тема с semantic tokens;
- export/backup конфигурации.

**Отложить:** автоматическое создание MCP для любой программы, свободное GUI-управление, большое количество субагентов, автономную перезапись identity/prompt, автоматическое принятие Instincts, обязательную vector DB, маркетплейс, multi-user/cloud sync, собственный генератор изображений при наличии внешнего provider/ComfyUI и сложную 3D-заставку до появления основного приложения.

# 23. Сквозные сценарии

## 23.1. «Почини проект EON»

1. Пользователь выбирает проект и задаёт цель.
2. CORE создаёт задачу и предлагает план.
3. MEMORY находит архитектуру, файлы и тестовые команды.
4. COMPASS выбирает модель для кодовой задачи.
5. AEGIS ограничивает доступ корнем проекта.
6. WINGS выполняет чтение/изменение/тесты.
7. CORE сравнивает ошибки до и после.
8. FORGE сохраняет diff и отчёт.
9. Verification перечисляет прошедшие тесты, непроверенные зоны и оставшиеся риски.

## 23.2. «Подключи FreeCAD»

1. Пользователь открывает BRIDGES.
2. Discovery обнаруживает приложение и варианты подключения.
3. SERAPHIM предлагает проверенный внешний `freecad-mcp` или иной способ.
4. Пользователь видит источник кода и запрашиваемые разрешения.
5. Интеграция сначала запускается изолированно/quarantine.
6. Проверяются соединение, capabilities и smoke workflow.
7. Пользователь разрешает управление тестовым документом.
8. Capability IDs попадают в WINGS Registry.
9. Создаётся/подключается FreeCAD Skill.
10. Результат проверяется по дереву CAD, геометрии и экспортированному файлу; screenshot — дополнительное доказательство.

## 23.3. «Создай Skill»

Пользователь выбирает шаблон → Studio создаёт пакет/manifest → пользователь задаёт workflow → связывает capabilities → LAB запускает тесты → AEGIS показывает запрошенные права → Skill остаётся draft до тестов/подтверждения → после включения COMPASS может его рекомендовать.

## 23.4. «Агент зациклился»

Recovery обнаруживает повтор tool call → CORE приостанавливает шаг → OBSERVATORY сохраняет последовательность → состояние приложения перепроверяется → модель получает краткую диагностику → разрешено ограниченное число recovery-попыток → задача либо возобновляется с новой стратегией, либо получает статус `BLOCKED` и требует вмешательства пользователя.

# 24. Риски и способы снижения

| Риск | Последствие | Мера |
|---|---|---|
| Слишком большой scope | Проект не достигает рабочего состояния | MVP и вертикальные сценарии |
| Слишком общая абстракция | Потеря специфики программ | Общие primitives плюс domain capabilities |
| Много процессов/языков | Сложность разработки и установки | Desktop-first runtime с ясными границами |
| Недоверенный MCP | RCE, утечки, порча файлов | Quarantine, least privilege, AEGIS, provenance |
| Ошибки модели | Неверные изменения | Verification, tests, diff, checkpoints |
| Красивый UI маскирует ошибку | Ложное доверие | Честные статусы и evidence trail |
| Плохая память | Устаревшие/ложные факты | Provenance, freshness, confidence, verification |
| Self-learning портит поведение | Непредсказуемая система | Candidate → test → review → accepted |
| Разбросанные конфиги | Сложная переносимость | Один корень и документированные исключения |
| Prompt injection | Неправильные действия | Разделение данных/инструкций и внешний policy engine |
| Ненадёжный adapter | Потеря данных | Sandbox, contract tests, approval |
| Чрезмерная анимация | Усталость и плохая читаемость | Reduced Motion и настройка интенсивности |
| Единственный provider | Зависимость от отказа | Provider abstraction и fallback |
| Плохой update | Потеря state | Backup, миграции и rollback |

# 26. Глоссарий

**Adapter** — связывает интерфейс SERAPHIM с API конкретного приложения.  
**Capability** — объявленная возможность интеграции с контрактом.  
**MCP** — протокол для стандартизированного предоставления инструментов и контекста клиентам/моделям.  
**Skill** — версия процедурных инструкций и ресурсов.  
**Tool** — вызываемая функция с валидируемой схемой и правами.  
**Task** — цель пользователя с планом, состоянием и результатом.  
**Step** — единица плана с зависимостями и проверками.  
**Checkpoint** — сохранённая точка для безопасного восстановления.  
**Evidence** — тест, diff, состояние API, файл, screenshot или лог, подтверждающие результат.  
**Provenance** — источник и путь происхождения факта/артефакта.  
**Instinct** — кандидат на повторно используемую эвристику.  
**Experience** — структурированное наблюдение о предыдущей работе.  
**Policy Engine** — компонент, независимо решающий допустимость действия.  
**Prompt injection** — попытка управлять агентом через недоверенные данные.  
**Recovery** — диагностика и восстановление после сбоя/отсутствия прогресса.  
**Workbench** — основная рабочая зона UI.  
**Vessel** — оболочка desktop-приложения.  
**Apocrypha** — экспериментальная зона, не включённая автоматически в стабильный runtime.

**SERAPHIM — не одна модель и не один огромный промпт. Это среда, в которой интеллект заменяем, действия ограничены политикой, состояние хранится вне контекста, память имеет происхождение, навыки версионируются, интеграции тестируются, а результат подтверждается наблюдаемыми доказательствами.**

Визуальная цель — кинематографичная, иммерсивная рабочая среда. Инженерная цель — обозримая, управляемая, расширяемая и восстанавливаемая система. Эти цели совместимы: интерфейс может выглядеть как пробуждение сложной сущности, но под ним должны быть честные статусы, понятные контракты и проверяемые действия.
