# SERAPHIM — Architecture Decision Records

**Версия:** 0.1
**Дата создания:** 13 октября 2026 (этап S01)
**Формат ADR:** контекст → варианты → решение → последствия → статус → дата пересмотра

## Статусы

| Статус | Значение |
|---|---|
| `ACCEPTED` | Решение принято и обязательно к исполнению |
| `PROPOSED` | Варианты проработаны, решение не принято — ждёт пользователя или прототипа |
| `PENDING-PROTOTYPE` | Спецификация (§18, §25) прямо требует прототипа перед решением |
| `SUPERSEDED` | Заменено другим ADR |
| `DEPRECATED` | Больше не действует |

**Правило S01:** ни одно решение, требующее прототипа, не принято молча. Спецификация §18: «Выбор делать после короткого технического прототипа». §25: «Открытые вопросы нельзя представлять как уже принятые технические решения».

## ADR-000 — Формат и жизненный цикл ADR

**Контекст.** Спецификация §25 требует ADR с обязательными полями и запрещает выдавать открытые вопросы за принятые решения. Нужен единый формат, иначе решения фрагментируются (риск №3 аудита).

**Варианты.**
1. Markdown-файл на ADR в `docs/adr/NNNN-*.md` (MADR-подобный).
2. Один файл `ARCHITECTURE_DECISIONS.md` со всеми записями.
3. YAML/JSON реестр решений в БД.

**Решение.** Вариант 2 для фазы контракта (один файл, обозримый_diff, inspectable по принципу «Everything is inspectable»). При росте числа ADR свыше ~25 — мигрировать в `docs/adr/` с индексом (миграция не ломает ссылки, т.к. ID стабильны).

**Последствия.**
+ Один diff на ревью; ID стабильны; пользователь читает один файл.
− Файл будет расти; конфликты при параллельных правках.

**Статус:** ACCEPTED
**Дата:** 13.10.2026 · **Пересмотр:** при переходе порога 25 ADR

## ADR-001 — Язык backend

**Контекст.** Спецификация §18 сознательно не выбрала язык: «Для backend выбрать один основной язык или чёткие границы: Python удобен для AI/MCP/интеграций, Rust — для отдельных системных компонентов, но много языков без необходимости увеличит сложность». Аудит относит выбор к критическим рискам №1 и №3. Окружение: Python 3.10.10, Node 24.18.0, Rust 1.97.1, .NET только preview, Java 21 LTS.

**Варианты.**
1. **Python** — экосистема AI/MCP, быстрый цикл интеграций. Минусы: packaging desktop-приложения, GIL для параллельных задач, контроль ресурсов subprocess.
2. **Rust** — единый язык с Tauri, сильный контроль изоляции/ресурсов. Минусы: скорость итераций по AI/MCP-экосистеме, выше цена ошибок на ранних этапах.
3. **C#/.NET** — нативный desktop на Windows. Минус: в среде только preview SDK 10.0.300; для production нужен .NET 8 LTS (риск аудита №4).
4. **Гибрид Python (ядро/интеграции) + Rust (изолятор/системные компоненты)** — принимается только если ADR-002 покажет реальную необходимость второго языка. Спецификация прямо предупреждает против лишней многоязычности.

**Решение.** Принят вариант 1: **Python как язык CORE backend**.

**Границы решения (актуализация после ревью S02):**
- ADR-001 выбирает **технологию (Python)**, а не конкретную версию runtime.
- S02 проводился на **Python 3.10.10 — это версия экспериментальной среды**, а не production baseline.
- Production runtime обязан использовать **поддерживаемую (supported) версию Python**, выбираемую при реализации production VESSEL/CORE из актуальных stable-веток. Версия фиксируется в production-конфигурации и lock-файлах на этапе S03+, а не на основании S02.
- Выбор Python не создаёт архитектурной зависимости от конкретного AI/MCP SDK: SERAPHIM CORE → MODEL PROVIDER / ADAPTER → MODEL / SDK. Смена SDK/провайдера не должна требовать смены языка или переписывания CORE.

**Подтверждение прототипом (S02):**
- Python stdlib-only backend (server.py + procman.py): **24/24 PASS** тестов.
- Health endpoint, config read from test root, path traversal blocked, LAN-only binding, Job Object subprocess isolation, structured error envelope — всё работает без внешних зависимостей.
- RTT 0.5ms loopback, auth token required.
- Job Object isolation (KILL_ON_JOB_CLOSE, memory limits, process count limits) работает без admin прав на Windows 11 Home.
- S02 доказал жизнеспособность Python как языка backend; конкретная версия среды (3.10.10) не является частью решения.

**Ограничения S02 (не проверено, не является blocker для ADR-001):**
- Path traversal blocked ≠ полная filesystem confinement: symlink confinement на Windows не проверен (Windows 11 Home без dev mode).
- Production packaging size не измерялся.
- Production версия Python не выбиралась.

**Последствия.**
- Python → нужен дисциплинированный packaging и lock-файлы; Tauri/Electron возможны только через IPC к отдельному процессу.
- Rust → медленнее Phase 1–7, проще Phase 2 (изоляция) и S76 (resilience) — но не используется как main backend.
- Гибрид → не применяется; один язык backend = Python.

**Статус:** **ACCEPTED**
**Дата:** 13.10.2026 (актуализировано после ревью S02 в тот же день) · **Пересмотр:** при пересмотре архитектуры (не ранее C8)

## ADR-002 — Desktop framework (VESSEL)

**Контекст.** §8 требует кинематографичные анимации, скан-линии, темы через semantic tokens, Reduced Motion, keyboard navigation, кириллическую типографику. §18: «Выбор делать после короткого технического прототипа». §8.1 запрещает превращать UI в декоративную заставку.

**Варианты.**
1. **Tauri** (Rust core + webview) — лёгкий бинарник, но webview-анимации и доступ к локальным путям требуют проверки.
2. **Electron** (Node + Chromium) — зрелая экосистема анимаций, большой размер, выше потребление ресурсов.
3. **Нативный стек** (Avalonia / Dear ImGui / WinUI) — контроль отрисовки; Avalonia требует .NET LTS (в среде только preview).

**Варианты backend-связки:** in-process библиотека (если один язык) vs локальный HTTP/IPC к отдельному процессу (если разные языки).

**Решение.** Принят вариант 2: **Electron как VESSEL technology**.

**Границы решения (актуализация после ревью S02):**
- ADR-002 выбирает **технологию (Electron)**, а не конкретную версию.
- S02 проводился на **Electron 33.2.0 — это версия экспериментальной среды**, а не production baseline.
- Production major/minor version будет выбрана из поддерживаемой stable-ветки Electron при реализации production VESSEL (S03+). Версия фиксируется в `package.json` production-сборки, а не на основании S02.
- Prototype НЕ мигрирует на новую версию Electron — эксперимент уже выполнил свою задачу.

**Подтверждение прототипом (S02):**
- `npm install electron@33.2.0` (experimental version) прошёл за 45 секунд, бинарник `electron.exe` доступен.
- Electron main.cjs успешно стартует Python backend, открывает window, загружает `index.html`.
- Round-trip UI→backend: RTT < 1ms.
- Tauri v2 prototype failed в текущей среде: `rc.exe` (Windows resource compiler) недоступен, требуется MSVC Build Tools (~5-10GB, админ-права). Tauri остаётся возможной будущей альтернативой, но Electron — принятая VESSEL technology для текущей реализации.
- Chromium bundled в Electron = детерминированный рендеринг анимаций (в отличие от WebView2, версия которого может варьироваться).

**Ограничения S02 (не проверено, не является blocker для ADR-002):**
- Production packaging size не измерялся.
- Electron auto-update не тестировался.
- Production версия Electron не выбиралась.

**Последствия.**
- Electron бинарник ~170MB (вместо ~5MB Tauri). Это осознанный компромисс.
- Chromium bundled = consistent rendering (важно для Spec §8.1: честные статусы, не маскирующие ошибки).
- Electron process model = separate process от backend (как и требовалось при разных языках).

**Статус:** **ACCEPTED**
**Дата:** 13.10.2026 (актуализировано после ревью S02 в тот же день) · **Пересмотр:** при пересмотре архитектуры (не ранее C8)

## ADR-003 — Внутренний и внешний API (GUI↔CORE)

**Контекст.** §14.3: GUI получает структурированное состояние и события, но не редактирует БД напрямую; изменения идут через API CORE/SANCTUM и проходят валидацию/политику. §18: «GUI↔CORE использует локальный API с ограничением доступа; управляющий endpoint не выставляется в сеть по умолчанию». CLI (раздел 13) — полноценный интерфейс, управляющий тем же состоянием, что и GUI (§0.2 инвариант 8).

**Варианты.**
1. In-process вызовы через общий слой сервисов (минимум слоёв, но UI и backend должны быть на одном языке).
2. Локальный HTTP/JSON только на loopback (универсально для CLI и UI, риск случайной экспозиции порта).
3. Локальный IPC (named pipe / unix socket) с аутентификацией токеном сессии.

**Решение.** Принят вариант 2: **локальный HTTP/JSON на 127.0.0.1 с ephemeral port и session token**.

**Подтверждение прототипом (S02):**
- Python backend: `HTTPServer(('127.0.0.1', 0), ...)` — ephemeral port, loopback only.
- Порт записывается в файл `.s02-port` для discovery UI.
- Auth: `X-Seraphim-Token` header (session token). Без токена — 401.
- LAN IP: `netstat` показывает только `127.0.0.1:PORT`; подключение к LAN IP отвергается.
- RTT: 0.5ms loopback (стабильно < 1ms).
- Electron main.cjs читает port из файла и делает `fetch()` с токеном.

**Обязательные инварианты (зафиксированы):**
- один и тот же набор операций для GUI и CLI;
- ни один клиент не пишет в БД напрямую;
- ни одна мутация не минует валидацию SANCTUM и политику AEGIS;
- endpoint не биндится вне loopback по умолчанию;
- события доставляются потоково, состояние — снимками (snapshot + event stream).

**Последствия.** Транспорт влияет на сериализацию (ADR-004) и на структуру S50 (VESSEL shell, navigation и UI API).

**Статус:** **ACCEPTED**
**Дата:** 13.10.2026 · **Пересмотр:** при пересмотре архитектуры (не ранее C8)

## ADR-004 — Сериализация схем и версия manifests

**Контекст.** §14 требует единые форматы ошибок и tool contracts; §4.9 прямо говорит: «Реальный формат требует формальной JSON Schema и миграций версий». §17 требует диапазоны поддерживаемых версий API.

**Варианты.**
1. JSON Schema как канон + YAML/JSON представления на диске.
2. Только dataclass-подобные модели в коде (схема выводится из кода).
3. Protobuf/FlatBuffers (эффективно, но плохо для человекочитаемых манифестов).

**Решение.** Принят вариант 2: **Python dataclasses с ручным `to_dict()`/`from_dict()` и `schema_version: int`**.

Обоснование:
- S03 установил **ноль production-зависимостей**; pydantic/jsonschema — внешняя зависимость, которая для ближайших этапов (S05–S10) не нужна: валидация через `__post_init__` с `SeraphimError` достаточна.
- Человекочитаемость (§1.1) достигается через dataclass-определения; YAML/JSON-представления на диске добавляются через `to_dict()`/`from_dict()`.
- Версионирование: `schema_version: int` на каждом persisted-объекте. Minor (опциональное поле) → consumer сохраняет unknown optional, игнорирует при обработке. Major (обязательное поле удалено/добавлено) → `CONTRACT_VERSION_UNSUPPORTED`.
- Round-trip safe: `_extra_fields` сохраняет неизвестные опциональные поля при десериализации.
- JSON Schema export отложен до момента, когда появится конкретный потребитель (S41 Integration Manifest, S34 Skill manifest).

Обязательные свойства (сохранены из предыдущей версии ADR):
- манифесты и конфиги человекочитаемы и редактируемы (§1.1);
- валидируемы вне рантайма (`seraphim config validate`, §12.4);
- версионируемы (`schema_version`);
- round-trip safe (сохранять неизвестные опциональные поля).

**Последствия.**
- Нет внешней библиотеки валидации — первая production-зависимость не вводится без обоснованной необходимости.
- При появлении JSON Schema consumers (S41) — export-утилита добавляется локально.
- Валидация — императивная (`__post_init__`), а не декларативная; для S04–S10 это адекватно.

**Статус:** **ACCEPTED**
**Дата:** 14.10.2026 · **Пересмотр:** при вводе JSON Schema consumer (S41+)

## ADR-005 — Изоляция shell / MCP / адаптеров

**Контекст.** §4.3 требует изоляции неизвестных адаптеров и MCP, лимитов CPU/памяти/тайм-аутов subprocess. §7.5 допускает quarantine-режим. Риск аудита №5: Windows 11 Home не имеет Hyper-V Manager GUI; Docker Desktop на Home имеет ограничения; WSL 2 доступен (2.6.3.0).

**Варианты.**
1. Ограничения процесса средствами ОС без гипервизора (Job Objects, Restricted Token, сниженные привилегии, рабочие папки-песочницы).
2. Контейнерный изолятор (Docker Desktop / WSL 2).
3. Отдельная VM.
4. Комбинация: уровень 1 по умолчанию, уровень 2 как опция для quarantine, уровень 3 для LAB-сценариев с опасными действиями.

**Решение.** НЕ ПРИНЯТО. Требует проверки на целевой машине (Windows 11 Home), что реально работает без админских прав. Обязательные инварианты независимо от выбора: неизвестный MCP/адаптер не получает доступа к другим MCP, памяти и диску; лимиты применяются даже в минимальном варианте; quarantine не является маркетинговым ярлыком.

**Последствия.** Если изолятор недоступен на Home-редакции, это надо сказать пользователю прямо, а не изображать изоляцию (§8.1 запрет на ложные статусы).

**Статус:** PENDING-PROTOTYPE
**Дата:** 13.10.2026 · **Пересмотр:** проверка среды в S02, окончательное решение до S20

## ADR-006 — Локальные модели и хранилище секретов

**Контекст.** Аудит относит оба вопроса к решениям, требующим выбора пользователя. §4.5: «API keys хранятся в защищённом хранилище/зашифрованном секрете, не в открытых логах». §12.1 допускает исключения для системных/защищённых данных, но требует, чтобы расположение было видимо пользователю. §1.1: секреты не обязаны быть открытым текстом, но способ управления обязан быть обозрим.

**Варианты (секреты).**
1. Windows Credential Manager — системное защищённое хранилище; минус: данные уходят за пределы единого корня SERAPHIM.
2. Зашифрованный файл внутри корня (например, наKeyring-подобной абстракции) — portable-режим сохраняется; минус: управление ключом шифрования.
3. Гибрид: абстракция `SecretStore` с двумя backend'ами, выбор пользователя.

**Варианты (локальные модели).**
1. Только внешние серверы (Ollama/llama.cpp/Strata) через provider interface — SERAPHIM их не запускает.
2. SERAPHIM управляет жизненным циклом локального сервера (start/stop/health).

**Решение.** НЕ ПРИНЯТО. Нужен выбор пользователя по обоим пунктам. Рекомендация агента (не решение): вариант «гибрид» для секретов и «только внешние серверы» для локальных моделей на MVP — это меньше всего нарушает единый корень и не добавляет процессов без необходимости.

**Последствия.** Вариант 1 для секретов конфликтует с portable-режимом (§12.2) и требует явного исключения в настройках.

**Статус:** PROPOSED
**Дата:** 13.10.2026 · **Пересмотр:** до S09

## ADR-007 — SQLite schema strategy и backup

**Контекст.** §6.1–6.2 задают SQLite как хранилище метаданных и динамического состояния и перечисляют ~30 целевых сущностей, прямо оговаривая: «Это целевая карта, а не требование создать все таблицы в нулевой миграции». §15 требует restore с проверкой совместимости и миграцией копии. CONTRACTS.md §6.2 фиксирует: transactional, forward-only, immutable checksummed migrations; rollback не поддерживается (восстановление = backup/restore).

**Варианты.**
1. Минимальные миграции по мере появления рабочих сценариев (соответствует §6.2).
2. Полная схема сразу (противоречит §6.2).
3. Без SQL-миграционного фреймворка, ручные скрипты (не обеспечивает инварианты).

**Решение.** ПРИНЯТО — вариант 1 (incremental forward-only migrations). Реализовано в S05: `seraphim.storage.migrations` — numbered registry, immutable checksummed `Migration` dataclass, transactional `MigrationRunner` (BEGIN/statements/postconditions/bookkeeping/COMMIT или ROLLBACK), idempotent reruns (skips applied versions), refusal-not-patch (rejects untrusted DB: missing bookkeeping table, unknown/gapped versions, edited checksums, schema from newer SERAPHIM). Первая миграция (m0001_kernel) создаёт 5 ядерных таблиц: schema_meta (version + installation_id), sessions, tasks (session FK CASCADE), events (OBSERVATORY), components (REGISTRY minimal metadata). State values (task/step/severity) НЕ ограничены CHECK: state machine owned by CONTRACTS/CORE (S16), эволюционирует быстрее immutable SQL. Rollback out of scope: recovery = backup + restore (§15, CONTRACTS §6.2).

**Обязательные инварианты (все реализованы):**
- Версионируемая нумерованная миграция: registry append-only, no edits, checksums recorded.
- Транзакционное применение: одна explicit transaction (BEGIN IMMEDIATE ... COMMIT) per migration; any failure → ROLLBACK всей миграции (statements + postconditions + bookkeeping + schema_meta upsert + PRAGMA user_version).
- Идемпотентность: applied versions skipped (read from schema_migrations), only pending executed.
- Отсутствие полусозданной схемы: transaction all-or-nothing → failed migration leaves DB = state before that migration.
- Test DB isolation: tests use tmp_path, no access to `<root>/data/seraphim.sqlite`.

**Последствия.** Ноль внешних зависимостей для миграций (raw sqlite3, CONTRACTS errors). Миграционный движок встроенный (`migrations/runner.py`), schema evolution = append to `MIGRATIONS` tuple. Parameterized queries throughout (ADR-007 implicit security contract: `guard_sql()` rejects multi-statement, interpolation markers, placeholder/param mismatch; `validate_identifier()` enforces ^[a-z_][a-z0-9_]*$ + reserved keyword check). Database path resolution: priority (1) explicit db_path arg, (2) SERAPHIM_DB_PATH env, (3) `<root>/data/seraphim.sqlite` default; relative overrides anchored at root (never escape SERAPHIM root unless allow_external=True).

**Статус:** ACCEPTED
**Дата:** 13.10.2026 (PROPOSED) → 15.10.2026 (ACCEPTED, S05 pass)
**Реализация:** S05 — `backend/seraphim/storage/` (db.py, paths.py, migrations/{base,runner,m0001_kernel}.py), 58 new tests, 232/232 PASS.

## ADR-010 — Обязательный security test suite

**Контекст.** §20.1 выделяет Security и Recovery как отдельные уровни; §20.2 содержит 20 golden-сценариев, из них минимум 8 security/recovery (№3, 9, 10, 12, 16, 17, 18, 20). Риск аудита №4: если AEGIS не встроен в базовый runtime, все интеграции потребуют рефакторинга.

**Варианты.**

**Варианты реализации:** отдельный маркер/тег тестов; отдельный набор файлов; обязательный gate на каждом checkpoint.

**Последствия.** Увеличивает объём тестов на каждом этапе; это осознанная плата за раннее обнаружение обходов.

## ADR-011 — Namespace capability IDs

## ADR-013 — Структура пакетов и запрет циклических импортов

**Контекст.** §2: модули — логические, не обязательные процессы. §0.2 инвариант 12 и §1.5 требуют вертикальных сценариев. CONTRACTS.md §3 задаёт 14 слоёв и запрет циклов. Без инструмента проверки запрет остаётся декларацией.

**Варианты.**
1. Один пакет, слои — соглашения в коде (циклы ловит только язык/линтер).
2. Пакет на модуль + проверка границ зависимостей на этапе lint/CI (import-linter, cargo module checks, architecture tests).
3. Пакет на модуль + отдельный contracts-пакет с интерфейсами (dependency inversion для WINGS/ToolProvider).

**Решение.** НЕ ПРИНЯТО (конкретный инструмент зависит от ADR-001). Обязательные инварианты:
- CONTRACTS-пакет не зависит ни от чего;
- зависимости только вниз по слоям CONTRACTS.md §3.1;
- наличие автоматизированной проверки архитектуры, запускаемой той же командой, что и тесты;
- composition root — единственное место, где собираются реализации `ToolProvider`.

**Последствия.** Стоимость: лишние файлы и слои абстракции на ранних этапах. Оправдание: без этого CORE неизбежно импортирует BRIDGES и возникает цикл.

**Статус:** PROPOSED
**Дата:** 13.10.2026 · **Пересмотр:** S02 (после ADR-001), подтверждение на C1

## ADR-014 — Модель процессов: single-process vs изоляция

**Контекст.** §2: «В MVP они могут быть частями одного приложения; процессную изоляцию добавлять там, где она повышает безопасность или устойчивость». §18: «выносить в отдельные процессы только ради изоляции, устойчивости или необходимости независимого рестарта». Риск аудита: «Много процессов/языков → сложность разработки и установки».

**Варианты.**
1. Единый backend-процесс для всех модулей.
2. Единый backend + отдельный процесс для недоверенного кода (внешние MCP, адаптеры в quarantine).
3. Много сервисов (отклонено: §18 запрещает вводить microservices без desktop-first необходимости).

**Решение.** НЕ ПРИНЯТО. Вероятный фаворит — вариант 2: недоверенный код обязан быть в отдельном процессе (иначе AEGIS нельзя честно назвать независимым policy engine, а §0.2 инвариант 2 не выполняется). Обязательные инварианты:
- ни один недоверенный компонент не работает в процессе CORE;
- UI и CORE могут быть одним процессом, если ADR-001/002 это допускают;
- OBSERVATORY не должен блокировать исполнение при своём сбое (§3.1).

**Последствия.** Вариант 2 требует IPC и корректной обработки смерти дочернего процесса уже в S37 (MCP GATEWAY).

**Статус:** PROPOSED
**Дата:** 13.10.2026 · **Пересмотр:** C1

## ADR-016 — Границы REGISTRY и доменных реестров

**Контекст.** Пробел спецификации: REGISTRY определён в §2 и упоминается в §4.8 («регистрация — контролируемая операция Registry»), §4.9 (Compatibility Registry), §16 (Project Registry), но не имеет раздела в §4. При этом SKILLS, BRIDGES и MODEL LAYER имеют собственные реестры.
