## 3. Риски и неизвестные вопросы

### 3.1. Критические риски

| # | Риск | Вероятность | Влияние | Мера |
|---|---|---|---|---|
| 1 | **Выбор стека (язык + UI framework)** — в спецификации отложен. Неправильный выбор на старте затруднит последующие интеграции (MCP, AI, desktop API). | Высокая | Критическое | Прототип системного доступа и benchmark Tauri vs Electron в Phase 0 |
| 2 | **Масштаб спецификации** — 27 разделов, 15 фаз, ~10 логических модулей. MVP (раздел 22) сужает, но риск «расползания» остаётся. | Высокая | Критическое | Строгое следование списку «Обязательно» в разделе 22; блокировка фаз 8+ до MVP |
| 3 | **Отсутствие git-репозитория** — нет истории, нет веток, нет CI. Начинать разработку без VCS рискованно для traceability. | Высокая | Высокое | Инициализация репо с `.gitignore` и начальной структурой до Phase 1 |
| 4 | **.NET SDK только preview-версии** — если выбран C#/Avalonia или подобный стек, preview не подходит для стабильной разработки. | Средняя | Высокое | Использовать .NET 8 LTS вместо preview; или выбрать Python/Rust |
| 5 | **Windows 11 Home** — нет групповых политик, нет Hyper-V Manager GUI, ограничения на домен. Для sandbox и изоляции MCP это может потребовать обходных решений (Docker, WSL, VirtualBox). | Средняя | Среднее | Проверить Docker Desktop на Home-версии; рассмотреть WSL 2 как sandbox |

### 3.2. Неизвестные вопросы, требующие решения

1. **Язык backend:** Python (удобнее для AI/MCP) vs Rust (производительность, Tauri) vs C# (нативный Windows).
2. **Desktop framework:** Tauri (Rust + web frontend, лёгкий бинарник) vs Electron (больше экосистемы, тяжелее) vs собственный native (Avalonia, Dear ImGui).
3. **SQLite vs файловое хранилище для MVP:** спецификация рекомендует SQLite, но требует ли это отдельной миграционной системы на старте?
4. **Локальные модели:** будет ли SERAPHIM запускать LLM локально (llama.cpp, Ollama) или только через провайдеры?
5. **Секреты:** Windows Credential Manager vs зашифрованный файл в корне — что предпочтительнее для desktop-first?

## 4. Ответы на обязательные вопросы

### 4.1. Какой код / инфраструктура уже существуют и что нужно сохранить?

**Ничего.** Репозиторий пуст — единственная существующая артефакт это `SERAPHIM_Full_Architecture_Spec.md`. Сохранять нечего, но спецификацию следует считать **источником истины** для всех последующих решений.

### 4.2. Каков стартовый статус git и какие изменения нельзя затронуть?

Git-репозиторий **не инициализирован**. Нет незакоммиченных изменений, потому что нет истории.

**Нельзя затронуть:**
- `SERAPHIM_Full_Architecture_Spec.md` — это единственный артефакт проекта. Его содержимое не должно быть изменено без явного указания (это baseline, а не черновик).
- Корневая директория `D:\Projects\seraphim\` — здесь нет пользовательских данных.

### 4.3. Какие пять главных рисков могут сделать следующие этапы неверными?

1. **Выбор стека без прототипа.** Если backend и UI выбраны без проверки системного доступа (MCP IPC, desktop API, GPU для vision), последующие фазы могут потребовать переписывания.
2. **Нарушение принципа «сначала MVP».** Создание фаз 8–14 до Phase 1 приведёт к «болоту» без рабочего цикла.
3. **Отсутствие ADR по языку и framework.** Без зафиксированных решений каждый этап будет принимать их заново, что приведёт к фрагментации.
4. **Игнорирование безопасности на старте.** Если AEGIS не встроен в базовый runtime, все последующие интеграции потребуют рефакторинга для поддержки политик.
5. **Отсутствие .gitignore и структуры проекта.** Без начальной структуры разработчик будет создавать файлы хаотично, что затруднит ревью и CI.

### 4.4. Какие решения требуют выбора пользователя, а какие агент может обосновать сам?

| Требуют выбора пользователя | Агент может обосновать и выбрать |
|---|---|
| Язык backend (Python / Rust / C# / другой) | Конкретные библиотеки в рамках выбранного языка |
| Desktop framework (Tauri / Electron / другой) | Структура каталогов в рамках выбранного framework |
| Будет ли локальный запуск LLM | Конкретный формат конфига для провайдеров |
| Целевая версия Python / Rust / .NET | Формат `.gitignore` |
| Начальная модель-провайдер для тестов | Формат YAML-конфигов |
| Стратегия безопасности секретов | Структура тестов |
